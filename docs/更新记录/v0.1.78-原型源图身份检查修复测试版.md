## 本次失败原因

v0.1.77已成功NETLOAD和握手，进入.NET采集、索引及候选追踪，最终被源图身份检查拦截。`output (32).zip`的原型JSON仅有 `SOURCE_CHANGED` 错误，变化事件数0、DBMOD始末均20。旧判断比较文档与数据库的托管包装引用是否相同；包装对象不是底层文档身份，同一原生对象使用不同包装时会误报。旧日志没有分开两项引用检查，无法断言具体是哪一项不同。

本轮改为分别比较起止文档和数据库的非零底层身份，托管包装引用差异只留作诊断。实际身份切换、对象变化事件、DBMOD变化仍会失败；身份缺失、已释放、无法读取或零值也停止处理。原型JSON新增 `source-guard` 分项和独立原因，便于下一轮直接定位。

同轮还发现失败归档误标：原型ERROR和LISP `VALIDATION_FAILED` 之后，日志却记为 `COLD-PROBE-FINISHED`。本版增加每轮独立的完成标志，仅在验证通过且对照报告写出后置为完成；无捕获错误且该标志为真才记录完成，其他情况记录失败。这样不依赖原生验证 `exit` 是否被catch识别为异常，也不会沿用上轮状态。

## 原图复测步骤

1. 新开AutoCAD会话，完整解压 `应急照明-v0.1.78.zip`，APPLOAD根目录 **ELCOLD78.lsp**，输入 **ELCOLD78**，默认选 `Prototype`。
2. 先拾取本次箱体 `2604F` 及五起点 `2606F / 260CD / 148A6 / 26060 / 26068`，保持原方向、配置及图纸副本，Enter完成。
3. 正常应显示原型耗时及报告路径。每轮结束或失败后立即运行 **ELDIAG**，保留完整诊断压缩包；失败时同时保留命令行错误。
4. 核对 `cold-probe.json` 的 `status=PROTOTYPE_COARSE_ONLY`、`source-guard` 原因列表为空，`cold-comparison.eld` 中COM边界抽查 `missing=0 / different=0`。候选数量是保守上界，不等于本箱实际设备数。
5. 再换其他新箱体，各轮单独留档。历史F072四起点另作一组，不能与本次五起点直接计算同条件提速比例。`Both` 可作同输入完整旧路径顺序参照，但不是严格冷A/B。

本版内部 `PACKAGE_NO=177`，后备目录 `%LOCALAPPDATA%/Emergency-Lighting/runtime-177/`、标记 `package-177.marker`。独立DLL为 `EmergencyLighting.ColdRecognition78.dll`；实际日志路径以命令行显示为准。正式面板入口 **ELFULL78.lsp → ELFULL78**。旧v77交付物、DLL及runtime-176保留，CADTools菜单不更新。
